# 논점 (nonjeom)

실제 시사 이슈를 매일 수집해 논술에 적합한 주제를 고르고, **문제 → 모범답안 → 논리 해설 → 다른 입장 → 학습 포인트**를 여러 단계의 검증을 거쳐 매일 오전 9시(한국시간)에 발행하는 서비스입니다. 사이트 이름은 `config/site.json`의 `name`(또는 저장소 변수 `NJ_SITE_NAME`)으로 바꿀 수 있습니다.

이 폴더는 같은 저장소의 기존 서비스(스타트업 뉴스 브리핑, 저장소 루트)와 독립된 패키지입니다. 기존 서비스의 파일·워크플로는 건드리지 않았습니다.

## 구조 한눈에 보기

```
GitHub Actions (예약·수동 실행, 서버에서 동작)
 ├─ 06:05 KST  daily   수집 → 묶기 → 선별(LLM) → 선정(코드) → 주제별 8단계 작성·검토 → ready 저장
 ├─ 08:47 KST  publish 09:00까지 대기 → ready 주제만 공개 데이터로 이동
 └─ 10:40 KST  recover 오늘 실패분·누락 날짜 복구(1회 상한)
        │
        ▼  결과를 git에 커밋(버전 관리·감사 기록)
 nonjeom/data/public/    발행물(정적 JSON) ──▶ GitHub Pages가 /nonjeom/ 에서 그대로 제공
 nonjeom/data/internal/  미발행 초안·검토 원문·수집 기록(AES-256-GCM 암호화)
 nonjeom/data/state/     잠금 등 운영 상태
```

| 위치 | 역할 |
|---|---|
| `src/collect/` | RSS·공식 발표 피드 수집, 시각 정규화(KST), 같은 사건 1차 묶기 |
| `src/llm/` | 제공자 교체 가능한 LLM 계층(Anthropic·OpenAI), 단계별 zod 스키마, 프롬프트(버전 기록), 일일 비용 상한 |
| `src/pipeline/` | 일일 오케스트레이터(잠금·체크포인트·재개), 선별·선정, 주제별 단계 기계, 코드 검사, 발행 차단 게이트 |
| `src/publish/` | 공개 데이터 생성, 버전·정정 이력, 운영 현황 |
| `src/eval/` | 테스트 전용 가상 데이터·LLM 대역, 결함 주입 검증 |
| `index.html`, `assets/` | 읽기·연습 화면(정적, 빌드 없음) |
| `config/` | 사이트·정책·수집원·모델 설정, 일시 중지 상태 |

### 왜 이 구조인가

- 기존 저장소가 이미 GitHub Actions 예약 실행 + 정적 JSON + GitHub Pages로 매일 운영되고 있어, 같은 방식을 따르면 **추가 서버·DB 비용 없이 바로 배포**할 수 있습니다.
- GitHub Actions 작업은 최대 6시간까지 실행되므로 장시간 생성·검토를 감당합니다(단계 타임아웃 270분, 실패해도 체크포인트 커밋 후 다음 실행이 이어서 처리).
- 저장소 자체가 영구 저장소이자 감사 기록입니다. 모든 발행·정정·실행 기록이 커밋으로 남습니다. `src/lib/store.js`의 함수만 바꾸면 다른 DB로 옮길 수 있습니다.
- 관리자 인증·인가는 GitHub 권한이 맡습니다. 수동 실행·재시도·일시 중지는 저장소 쓰기 권한이 있는 사람만 Actions 화면에서 할 수 있습니다.

## 매일 무엇이 일어나나

1. **수집**: `config/sources.json`의 정책브리핑(공식 자료)·통신사·신문·방송·해외 언론·Google 뉴스 묶음 피드를 읽습니다. 수집 대상은 전날 00:00~당일 00:00(KST)이며, 지연 보도 보완을 위해 72시간을 겹쳐 검색합니다. 해외 기사 시각은 KST로 변환합니다. 게시일·수정일·실제 사건일을 따로 저장합니다.
2. **묶기**: 제목 유사도로 같은 사건 기사를 묶고, 이전 발행호에서 이미 처리한 기사만 있는 묶음은 제외합니다.
3. **선별(LLM, 별도 호출)**: 사건일, 기존 이슈 묶음과의 관계(새 이슈 / 의미 있는 후속 / 사소한 업데이트 / 중복), 공공성·가치 충돌·논증 여지·근거 확보 가능성·개념적 중요성을 평가합니다. 기사 수·검색 순위는 점수에 넣지 않습니다.
4. **선정(코드)**: 가중 점수 + 새로움, 최소 기준 미달 제외, 최근 7일 분야 쏠림 보정, 같은 분야 상한. 목표(기본 3~5개)를 채우려고 기준을 낮추지 않습니다. 사소한 업데이트는 기존 이슈의 "이어지는 소식"으로만 연결합니다.
5. **주제별 8단계**(각각 별도 호출·별도 역할, 결과 저장 후 재개 가능)
   ① 자료 수집·사실 정리(원문 본문 조회, 사실/주장/예정 구분, 접근 범위 표시) → ② 문제·평가 기준 → ③ 논증 설계 → ④ 초안 → ⑤ 사실 검증(원출처 대조) → ⑥ 논리 비판(18개 항목 체크) → ⑦ 수정(최대 2회, 수정 후 전체 재검토) → 해설·다른 입장·학습 포인트 → ⑧ 최종 검토·발행 판단
6. **게이트(코드)**: 중대한 사실 오류, 근거 없거나 출처와 어긋나는 사실 진술, 지어낸 수치·인용, 진행 단계 오기, 핵심 모순, 발문 미충족, 분량 미달, 최근 문제와 중복, 최종 검토 보류가 하나라도 남으면 **점수와 무관하게** 발행하지 않고 "검토 보류"로 남깁니다.
7. **발행**: 09:00에 ready 주제만 공개합니다. 생성이 늦으면 공개하지 않고 "발행 지연"을 표시하며 직전 정상 발행호를 유지합니다.

상태는 다음처럼 구분됩니다: `published`/`partial`(일부 보류) · `no_qualifying_topics`(기준 통과 새 주제 없음) · `all_held`(검토 미통과) · `failed_collect`/`failed_generation`(작업 오류) · `budget_deferred`(비용 상한) · `paused` · `delayed`.

## 실행 방법

Node.js 22.9+ 와 pnpm 11.7이 필요합니다(저장소 루트에서 설치).

```bash
pnpm install --frozen-lockfile          # 저장소 루트에서
cd nonjeom
cp .env.example .env                    # 값 채우기(커밋 금지)
pnpm test                               # 오프라인 테스트(35개, API 키 불필요)
pnpm fixture:site                       # 가상 데이터로 전체 파이프라인 실행 → data/fixtures/public
pnpm probe                              # 수집원 응답 확인
pnpm daily -- --date 2026-11-08         # 실제 생성(API 키 필요, 비용 발생)
pnpm publish -- --date 2026-11-08       # 발행 시각이 지났으면 공개
pnpm status                             # 운영 현황·누락 날짜
pnpm eval:adversarial                   # 결함 주입 사례를 실제 검토 모델로 검증(비용 발생)
```

화면 확인: 저장소 루트에서 `pnpm start` → `http://127.0.0.1:4173/nonjeom/` (견본 데이터는 `?data=fixtures`).

## 배포·운영 설정(사용자가 해야 하는 일)

1. **GitHub Secrets** (Settings → Secrets and variables → Actions → Secrets)
   - `ANTHROPIC_API_KEY` — 필수. Anthropic Console에서 발급.
   - `NJ_INTERNAL_KEY` — 필수. `openssl rand -base64 32`로 만든 24자 이상 문자열. 공개 저장소에 내부 기록을 암호화해 커밋하는 데 씁니다. 잃어버리면 이전 내부 기록을 읽을 수 없습니다.
   - `OPENAI_API_KEY` — 선택. 검토 역할을 다른 회사 모델로 분리할 때만.
2. **워크플로 활성화**: `.github/workflows/nonjeom.yml`이 기본 브랜치(main)에 있어야 예약 실행이 등록됩니다. 병합 후 Actions 탭에서 "논점 — 일일 논술 발행"을 한 번 수동 실행(action=daily)해 첫 호를 만들고 결과를 확인하세요.
3. **GitHub Pages**: 기존 사이트가 브랜치에서 배포되고 있다면 `https://<사용자>.github.io/<저장소>/nonjeom/`에서 바로 열립니다.
4. (선택) **Variables**: `NJ_TOPICS_MIN/MAX`, `NJ_DAILY_USD_CAP`, `NJ_ANSWER_MIN/MAX_CHARS`, `NJ_PAUSED`, 역할별 모델(`NJ_REVIEWER_PROVIDER` 등). 목록은 `.env.example`.

관리 작업은 [docs/OPERATIONS.md](docs/OPERATIONS.md)를 보세요.

## 모델과 비용

- 기본: 모든 역할 `claude-opus-5-5`(Anthropic 공식 SDK, 스트리밍, structured outputs, 적응형 사고 + effort, 안전 분류기 거절 시 서버 측 대체 모델 `fallbacks: "default"`). 모델·단가 출처는 `config/models.json`.
- 검토 역할을 같은 모델로 하면 화면에 **"같은 모델의 별도 호출 — 독립 검증은 아님"**으로 표시합니다. 다른 회사 모델로 바꾸면 그에 맞게 표시됩니다.
- **추정 비용**(실측 전 추정치): 주제 1개당 LLM 호출 12~16회. 입력 약 20만~25만 토큰($4/M), 출력(사고 토큰 포함) 약 10만~13만 토큰($20/M) → **주제당 약 $3(±50%)**, 선별 약 $0.7. 하루 4개 발행 기준 **약 $10~18/일**, 월 $300~550. 실제 사용량은 실행 기록(`runs/*`)과 주제별 `usage`에 남으므로 첫 주 실측으로 조정하세요. `NJ_DAILY_USD_CAP`(기본 $20)에 가까워지면 새 주제 작성을 멈춥니다(검토는 생략하지 않음). 비용을 줄이려면 작성·검토 모델을 `claude-sonnet-5-5`($2/$10)로 바꾸는 선택지가 있으나 품질 영향은 직접 비교해 판단해야 합니다.
- GitHub Actions: 공개 저장소는 무료. 비공개 저장소는 하루 1~3시간 실행 기준 월 30~90시간이 사용량에 잡힙니다.

## 검증한 것과 하지 못한 것

- ✅ 오프라인 테스트 35개: KST 날짜 경계·해외 시각 변환, SSRF 차단, RSS 파싱, 코드 검사(수치·인용 날조, 분량, 요구사항, 상투적 결론, 중복), 게이트 차단 규칙, 선정 규칙(후속/중복/늦은 사건/분야 편중), 전체 흐름(09시 전 비공개 → 09시 발행, 재실행 중복 없음, 수집 실패 시 직전 호 유지, LLM 오류 후 실패 단계부터 재개, 잠금·만료 회수, 비용 상한, 일시 중지, 누락 날짜 복구, 정정 버전, 내부 기록 암호화).
- ✅ 가상 데이터로 실제 파이프라인 코드 전체 실행 → `data/fixtures/public` (화면 견본, 모든 항목 `test: true`, 화면 상단 경고 띠).
- ⏳ 실제 뉴스 수집과 실제 LLM 호출은 개발 환경의 네트워크 제한과 API 키 부재로 **아직 한 번도 실행하지 않았습니다.** 첫 실행 결과는 Actions 로그와 `운영 현황` 화면에서 확인해야 합니다.
- ⏳ `pnpm eval:adversarial`(결함 8종을 실제 검토 모델이 잡는지)은 키가 있어야 실행되며 결과는 `docs/adversarial-report.md`에 기록됩니다. 코드 검사로 잡히는 결함(수치·인용 날조)은 오프라인 테스트로 확인했습니다.

## 남은 한계

- RSS는 보통 최근 1~2일 기사만 제공하므로, 며칠 지난 날짜를 복구하면 수집되는 기사가 적어 "주제 없음"이 될 수 있습니다.
- 기사 본문 추출은 일반 규칙 기반이라 일부 언론사는 발췌만 확인됩니다(화면에 확인 범위로 표시). 공식 원문(법령·판결문 PDF 등)을 직접 따라가 읽는 기능은 없습니다.
- 같은 사건의 한국어·영어 기사는 1차 묶기에서 따로 묶이며, 선별 LLM의 병합 판단에 의존합니다.
- 자동 검토는 제공된 출처 범위 안에서만 사실을 확인합니다. 출처 자체의 오류나 미묘한 맥락 왜곡은 놓칠 수 있습니다.
- 내 답안·북마크는 브라우저에만 저장됩니다(서버 저장·로그인 없음). 자동 첨삭은 아직 없습니다.
- GitHub 예약 실행은 혼잡 시 늦게 시작될 수 있습니다. 그래서 생성은 3시간 앞서 시작합니다.
